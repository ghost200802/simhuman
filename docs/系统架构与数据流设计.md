# SimHuman 程序架构：JS 分层与数据流约束

**定位：** 描述 JS 侧如何分层、数据流有哪些约束，目标是"表现层稳定，核心日后可整体平移为 Rust"。
**边界：** 计量数值、科技树、UI 与具体存档格式不在此文。阅读可脱离其他文档。

**一句话：** 游戏是单机实时模拟（类维多利亚 3）。**核心持有唯一权威数据并推进 tick，表现层只渲染与翻译输入**。核心先用 TS 实现，但其分层、数据形态与接口都按"将整体重写为 Rust"来设计——迁移时只换核心实现，表现层不动。

---

## 0. 内核模型：效果与 Modifier（P 社式）

先把世界观定对，避免把"玩家命令"混进 tick：

- 世界的状态 = **数值 + Modifier + 进行中事项**。
- **Modifier**＝作用在某个作用域实体（政权/区块/聚落/建筑/人口…）上的数值加成容器。来源可为建筑、政策/法律、科技、事件、国策等；可常驻或限时（日/月/年）、可堆叠/衰减；类型一律定义在 JSON 数据表（类似 V3 的 modifier types）。
- **效果（Effect）**＝对数据的一次改动：立即增减数值、施加/移除 Modifier、开启或推进一个进行中事项。玩家操作、事件触发、进度完成，最终都汇入**同一套效果执行**。
- **Tick 只模拟数据**：聚合当前所有有效 Modifier → 得到"当前生效值" → 结算生产/消耗/人口/压力等 → 推进进行中事项（到期移除 Modifier、完成时触发一次效果）→ 确定性触发随机事件。
  **tick 内部不存在"命令"对象**：玩家按下那一刻，命令已在入口被折成效果，操作意图不会活到 tick 里。

P 社做法佐证：效果按作用域施加 modifier（可带 duration / 衰减 / 堆叠），每日 tick 只做经济、外交与 modifier 的聚合推进与到期处理，没有"执行玩家点击队列"这一环。

## 1. 三层分层（JS 侧）

### L0 共享契约与配置
- **契约**：`Command / Diff / Event / Query / Snapshot` 结构定义，带版本号。`Command` 只是"输入事件"，到达核心即被翻译成效果，**不进入 tick**。TS 一份类型；日后 Rust 用同一份 schema（serde）对齐。
- **配置 JSON**：所有数值、**Modifier 类型定义**、进行中事项定义，以及内容表（建筑/资源/科技/政策/事件）。核心零魔法数值。

### L1 模拟核心（Core）
- 唯一权威状态：数值字段 + Modifier 列表 + 进行中事项 + 确定性 PRNG。
- 对外窄接口：
  - `initWorld(seed, config) -> World`
  - `applyCommand(world, cmd)` —— **入口薄层，不在 tick 内**：把玩家/系统操作翻译成效果并立即落地（改数值、加/移 Modifier、开启进度项），记入命令日志（带 tick 时刻）。
  - `step(world)` —— **纯模拟**推进一个（或 N 个）固定 tick：聚合 Modifier → 结算规则 → 推进进度 → 产出 `diff/event`。内部无任何 command 语义。
  - `query(world, q)`——只读，不推进
  - `serialize(world)` / `loadWorld(data)`
- 内部组织（模块化、无跨模块可变环）：
  - `rng.ts`：确定性 PRNG（由种子派生）。
  - `world.ts`：状态数据与构造。
  - `mods.ts`：Modifier 聚合求值（作用域 → 当前生效值）。
  - `progress.ts`：进行中事项（推进、到期、完成效果）。
  - `effects.ts`：效果执行——`applyCommand`、事件触发、进度完成共用，对应日后 Rust 的一个 module。
  - `systems/`：领域纯规则（人口、生产、探索、政权、事件触发…），各是 `(world, ctx)` 的推进函数。
  - `tick.ts`：逐 tick 调用 mods/progress/systems，汇总 diff/event。

### L2 表现层（Cocos 视图）
- 职责：渲染、UI、输入捕捉、把玩家意图翻译成 `Command` 发给核心入口，把 `diff/event` 应用到**视图模型**。
- 不判定规则、不直接改核心状态；只持有派生的视图模型，可随时被快照覆盖。
- 控制器与视图分离：UI 组件只走"派发命令 / 发起查询"两个薄接口，不直接摸核心数据。

## 2. 核心"方便日后迁 Rust"的编写约束

1. **状态是可序列化的纯数据**：数值字段、Modifier、进行中事项都是普通 record/数组 + 整数 ID；不用 class 内部闭包跨 tick 持状态、不用继承层次 → 对应 Rust struct。
2. **逻辑是纯函数/模块函数**：`applyCommand` 与 `step` 的结果只依赖入参与已记录的 rng 序列；不读全局、不碰 `Date/random/DOM` → 对应 Rust 纯函数模块。
3. **按领域小文件拆模块**，各自独立可测，模块间只经显式字段/ID 交互 → 对应 Rust module 边界。
4. **实体用稳定整数 ID + 版本号**；跨层只传 ID 与结构化增量，不共享可变引用。
5. **数值与 Modifier 定义全部走 L0 JSON**，init 时注入 → Rust 用 serde 直读同一份 JSON。
6. **确定性**：同种子 + 同（applyCommand + tick 时刻）序列 ⇒ 同结果，天然支持回放/存档/迁移等价测试。随机只在 tick 内由注入的 rng 产生。
7. **核心目录无任何 Cocos/平台 import** → 整包可拷进 Rust 项目当"规格 + 测试基准"。
8. 关键算法若先做性能原型，标 `// PERF` 供迁移期优化。

## 3. 数据流与同步纪律

```
玩家操作 → [L2] 翻译成 Command
        → [L1] applyCommand：立即把效果落到数据（改数值 / 加 Modifier / 开进度项）
        → 时间流逝 → [L1] step：纯模拟推进 N tick（聚合 Modifier → 结算 → 推进进度）
        → diff / event → [L2] 更新视图模型 → 渲染
```

- 持续行为（建设、探索、改革、臣服、开化、政权过渡…）**不是"命令排队逐条执行"**：命令先落成一个"进行中事项（+ 起始 Modifier）"，tick 只推进它的进度，完成时触发一次效果。
- 只读查询走 `Query`（不推进模拟）；新局/读档/回放走 `Session`。
- **单一权威在 Core**：表现层只消费快照与增量，任何时刻都可由"全量基准 + 之后增量"重建。
- 每渲染帧推进的 tick 数由**速度倍率**决定，暂停 = 0；步进过大时分片摊还防卡。
- 时间流速只改变推进节奏，不改变 tick 内的确定性。
- 表现层想显示聚合（如区块概要）：向 Core 发 `Query` 或消费其预聚合，不自己从原始态推导。

## 4. 边界红线（core 目录内严禁）

- 引用 `cc` / 任何引擎或平台 API；
- 规则路径里用 `Math.random`、`Date.now`、任何 IO；
- 除 L0 JSON 外自行生成数值；
- 把渲染对象或回调传进核心；
- **在 `step` 内出现"if 玩家命令"类分支**——命令意图必须在入口消化为效果，否则破坏纯模拟与可迁移性。

违反任意一条都会同时破坏"可迁移"与"可测试"两条基线。

---

## 5. 存档、回放与迁移测试

- **本局存档** = `serialize(World)` + 种子 + 命令日志（每个命令带其生效的 tick 时刻）；读档恢复核心，表现层由全量快照重建。
- **局外档案**（局外点数/时代特性/成就）单独存储，不放进核心。
- **回放**：记录命令流，可在任意版本重放并比对结果——既是排查工具，也是 **TS→Rust 等价性测试**：把 TS 期的回放日志直接喂 Rust 核心，结果必须一致。

---

## 6. 与 Cocos 工程的组织

目录建议：`assets/scripts/` 下分两块——
- `sim-core/`：L0 + L1，纯 TS、无 `cc` import，可独立跑测试与 CI；
- `view/`：Cocos 场景与 UI 脚本。

保持核心与视图物理隔离，迁移 Rust 时只替换 `sim-core/`。
