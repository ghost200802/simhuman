# SimHuman 底层方案与模拟内核

**定位：** 描述游戏的底层数据模型、模拟内核、系统拆分与配置驱动方式。
**边界：** 具体数值、科技内容、界面与美术不在此文。本文可脱离其他文档独立阅读。

**一句话：** 世界是一组**纯数据实体**，模拟是**一组按固定顺序执行的纯函数系统**，玩家命令与事件在进入模拟之前先被折算成对数据的**效果**。所有数值与内容来自**配置表**，核心代码零魔法数值。

---

## 1. 内核模型

世界的状态只有三种东西：

> **状态 = 数值 + Modifier + 进行中事项**

- **数值**：存在实体上的普通字段。快照、存档、回滚的基本单位。
- **Modifier**：作用在某个实体上的加成容器，可常驻或限时，可堆叠或衰减。来源是建筑、政策、科技、事件、时代特性等。
- **进行中事项**：需要跨 tick 才能完成的事，含建设、探索、改革、臣服、开化、政权过渡。推进到完成时触发一次效果。

对世界的一切改动，无论来源，都表示成**效果**。效果有三个来源：玩家命令、事件触发、进行中事项完成。它们汇入同一个执行器。

模拟只有一件事：**推进 tick**。tick 内部不存在「命令」这个概念 —— 玩家按下按钮那一刻，命令已经在入口被折成了效果。

## 2. 实体模型

采用 **Entity + System** 两层：实体只装数据，逻辑全在系统里。不引入 ECS 的 Component 层。

**为什么可以去掉 Component：** ECS 的组件解决的是「运行时能力组合」。本项目的实体能力来自**配置表 + Modifier** —— 一个建筑产出什么由配置里的 modifiers 决定，一项政策改变什么由配置里的效果决定。组合能力已经由配置机制承担，再引入类型化组件就是同一件事做两套。

### 2.1 Entity 数据规范

1. **实体是纯数据，不带方法。** 用具名接口 + 工厂函数，不用 class。class 实例经 JSON 往返后 `instanceof` 失效，会让存档和回放静默出错。
2. **实体之间只存 ID，不存对象引用。** 跨实体访问一律经 ID 查表。
3. **实体不持有闭包、回调、渲染对象或任何引擎对象。**
4. **所有字段都必须可序列化。** 判据：`JSON.parse(JSON.stringify(x))` 能无损还原。
5. **类型判别用 `kind` 字段做联合类型**，不用 `instanceof`、不用原型链。

### 2.2 实体清单

| 实体 | 承载什么 | 生命周期 |
| --- | --- | --- |
| **文明** | 技术积累、知识、语言与文化认同 —— 跨越政权更替而存续的底层 | 开局创建；文明灭绝时本局结束 |
| **政权** | 政体、政策、财政、合法性、军队，以及治下人口与建筑的归属 | 可反复生灭；玩家领导其中一个 |
| **大地块** | 地形与气候属性、资源配额与品味、小地块容量与已解锁数、探索度、邻接关系 | 玩家抵达时按需生成，之后长期存在 |
| **建筑** | 占用的小地块数、所属政权与大地块、运行状态、催动的 Modifier | 建造中 → 运行 → 损毁或废弃 |
| **人口** | 归属政权与大地块、数量、臣服、开化、族属、职业适合性 | 增长、死亡、迁移、被征服或开化 |
| **进行中事项** | 目标、进度、速率修正、完成与取消时的效果 | 创建 → 推进 → 完成或取消 |

**文明与政权必须分开。** 政权更替不等于本局结束：技术积累在文明层，政权更替时被继承；土地、资源所有权与旧债在政权层，更替时重新分配。政体是政权的一个字段，属于治理方案，可在相近技术条件下调整。

### 2.3 刻意不做成实体的东西

以下概念在数据模型里**不是实体**，这是有意的简化：

- **小地块（建筑格）** —— 需求已规定其内部完全等价、无坐标差异。因此它只是大地块上的两个计数：`容量` 与 `已解锁数`。建筑占用小地块就是把自己计入占用计数，**不需要记录"占的是哪一格"**，因为格子之间没有区别。
- **聚落** —— 与已开发的大地块一一对应，独立成实体会引入 `tileId ↔ settlementId` 的双向同步负担。而且多个政权可以共存于同一大地块（玩家建筑与原住民建筑分占槽位），"聚落"在这里本就是多义的。开发状态直接由该地块上的建筑与人口表达。
- **家庭、个人** —— 早期原型不逐人模拟，人口以同质群体为单位。
- **市场、贸易路线** —— 在需要之前，先作为政权与大地块上的字段存在。

**新增实体的判据：** 它是否需要独立的生命周期、需要被别的实体单独引用、需要单独挂 Modifier。三条都不满足，就说明它应该是某个实体的字段。

### 2.4 身份与引用

- 实体 ID 为 `(种类, 槽位序号, 世代号)` 三元组，可打包成单个整数。
- **世代号用于识别悬空引用：** 实体销毁后其槽位会被复用，世代号自增。持旧 ID 访问时世代不匹配，即判定引用已失效，而不是读到另一个实体。
- 遍历顺序必须确定：实体按 ID 升序排列，或按创建顺序维护在定长数组里。**任何依赖遍历顺序的规则都必须显式声明这个顺序。**

## 3. 效果与 Modifier

### 3.1 Modifier

Modifier 是**数值总线**：绝大多数长期效果不直接改数值，而是挂一个 Modifier，由内核在每 tick 聚合出「当前生效值」。

- 定义（有哪些类型、影响哪个字段、如何叠加）在配置表里，代码里没有 Modifier 类型的硬编码。
- 实例存在**它作用的实体自己身上**（`Realm.mods`、`Tile.mods`）。世界级效果（时代、全球事件）存在世界层。
- 每个实例记录：类型、数值、来源、剩余时长（或永久）、堆叠标签。
- **聚合是每 tick 的热点。** 聚合结果应缓存，只在实体数据变脏时重算，不要每 tick 全量重算每个实体。

Modifier 一旦失效（到期、来源建筑被毁、政策被废），其加成必须立即从生效值里消失。**"来源失效"和"到期"走同一条移除路径**，不要写两套。

### 3.2 效果

效果是对世界数据的一次确定性改动。类别如下：

| 类别 | 做什么 |
| --- | --- |
| 数值 | 对某实体的某数值字段做 加 / 设 / 乘 / 钳制 |
| Modifier | 施加、移除、刷新时长、按来源批量清除 |
| 进行中事项 | 开启、推进、取消、立即完成 |
| 实体 | 生成、销毁、变更归属 |
| 事件 | 触发、排队到后续 tick |
| 控制 | 条件分支、加权随机选择、对一组作用域批量执行 |

表达方式：

- 控制类效果在 JSON 里用嵌套结构（`if / then / else`、`for_each`、`weighted_random`）。数组顺序即执行顺序，必须确定。
- **复杂逻辑抽成命名效果组。** 配置表里放一张「效果组」表，效果可以引用效果组，避免 JSON 深度嵌套到不可读。
- 效果执行器**只有一个**，玩家命令、事件、事项完成全部走它。任何"绕过执行器直接改数据"的代码都是在制造第二套语义。

### 3.3 进行中事项

统一为**一个模型**：有目标进度的一次性事项，外加一个 `repeat` 标志。

- `repeat = false`：进度到满即完成，触发完成效果，事项结束。（建设、改革、政权过渡）
- `repeat = true`：进度到满即触发效果，然后**进度归零重新开始**，直到被显式取消或达到上限。（探索解锁小地块、持续选育种子、文化同化）

这个统一很重要：需求里「某些计量值只能通过持续执行逐步推进、不能靠一次研究瞬间获得」的那些过程，本质上就是 `repeat` 事项，不需要为它们另立一套机制。

推进速率 = 基础速率 × 该事项上的速率 Modifier。**建造耗时会被生产效率、政体、时代特性影响，这走的就是普通 Modifier，不写特例。**

### 3.4 命令不是模拟的一部分

```
玩家操作 → [表现层] 翻译成 Command
        → [核心入口] 折成效果并立即落地，记入命令日志（带生效 tick）
        → 时间流逝 → [tick] 纯模拟推进
        → diff / event → [表现层] 更新视图模型
```

- `applyCommand` 是入口薄层，**不在 tick 内**。
- 持续行为（建设、探索、改革、臣服、开化、政权过渡）**不是命令排队逐条执行**：命令先落成一个进行中事项（外加起始 Modifier），tick 只推进它的进度。
- **tick 内不得出现 `if (某玩家命令)` 类分支。** 出现即意味着命令意图活到了 tick 里，会同时破坏确定性和可测试性。

## 4. 时间与 tick

### 4.1 统一 tick 与时代时间尺度

**tick 是固定的抽象步长，所有配置速率一律以「每 tick」为单位。**

时代决定的是「1 tick 代表多久」（`tickYears`），这个值**只用于换算显示年代、事件冷却的真实跨度、代际更替的判断**，不参与速率计算。

这样做的理由：

- 配置的语义稳定 —— 一个"每 tick 产 2 单位"的设施在任何时代都是同一句话。
- 模拟规则全程一致，时代切换不触发任何特例分支。
- 若让时代缩放速率，每次时代转换都要重算全部配置，且浮点误差会累积进确定性。

**必须接受的后果：** 早期 1 tick 可能代表十年，工业期 1 tick 代表一个月。这意味着同样跑 100 tick，前者跨过一千年，后者只跨过八年 —— 游戏在后期"变慢"是模型自带的，不是 bug。如果某个时代 100 tick 内什么都做不完，那是**该时代的配置速率需要单独调**，不是模型问题。

**快进：** `step(world, N)` 一次推进 N 个 tick，速度倍率为 0 时即暂停。快进只改变推进节奏，不改变任何 tick 内的结果。步长过大时按固定分片摊还，避免卡帧。

### 4.2 tick 顺序表

**顺序本身就是规则。** 生产必须在消费之前，人口必须在消费之后，压力必须在人口之后 —— 改动顺序就改动了模拟结果。因此顺序必须**显式写在一处**，而不是让每个系统自行注册。

| # | 阶段 | 为什么在这个位置 |
| --- | --- | --- |
| 1 | 时间与时代推进 | 先确定本 tick 的时间尺度与时代状态 |
| 2 | Modifier 聚合 | 得出各作用域的「当前生效值」，供后续所有阶段读取 |
| 3 | 生产 | 设施产出进入库存；占用人工 |
| 4 | 消费与维护 | 人口吃粮、建筑维护、运输消耗；本 tick 可用量在此确定 |
| 5 | 人口 | 出生、死亡、迁移 —— 依赖 4 的结果判断生存状况 |
| 6 | 探索与扩张 | 推进大地块的解锁度与探索度，揭示资源 |
| 7 | 进行中事项 | 推进进度、到期移除 Modifier、完成时触发效果 |
| 8 | 压力累积 | 人口压力、土地集中、财政失衡、统治集团腐化 |
| 9 | 政权 | 更替、分裂、合流判定 |
| 10 | 事件 | 按确定性 PRNG 抽取并触发 |
| 11 | 汇总 | 产出 diff 与 event，供表现层消费 |

效果执行器（3.2）被 3–10 中任何一个阶段调用，但它本身不是 tick 的一个阶段。

### 4.3 确定性

- 同种子 + 同（命令序列 + 生效 tick 时刻）⇒ 同结果。这是回放、存档、迁移等价测试共同的基线。
- 随机**只在 tick 内**由注入的 PRNG 产生；PRNG 状态是 `World` 的一部分，随存档保存。
- 规则路径禁止 `Math.random`、`Date.now`、任何 IO、任何全局可变状态。
- **抽取顺序必须固定**：随机数消耗的次数与顺序一旦依赖遍历顺序，遍历顺序就成了规则的一部分（见 2.4）。
- **避免在规则路径使用超越函数。** `Math.pow` / `exp` / `sin` 在不同实现间结果可能有差异，会破坏跨实现等价。需要时把它们封进一个可替换的数学库，标 `// PERF` 或 `// PORT` 单独处理。

## 5. 系统拆分

分成两类：内核设施与阶段系统。

### 5.1 内核设施（不是 tick 阶段）

| 设施 | 职责 |
| --- | --- |
| Modifier 聚合器 | 作用域 → 当前生效值；维护缓存与失效 |
| 效果执行器 | 执行效果，唯一的改动入口 |
| 事项推进器 | 推进进行中事项，处理到期与完成 |
| 查询层 | 只读访问，不推进模拟 |
| 序列化 | `World` ↔ 字节，双向无损 |

### 5.2 阶段系统

每个阶段系统是 `(world, ctx) => void` 形式的纯函数，只做本领域的事，通过效果执行器或直接写自己负责的字段来产出结果。

| 系统 | 读 | 写 |
| --- | --- | --- |
| 时间与时代 | 文明 | 世界 tick、当前时代 |
| 生产 | 建筑、人口、资源配额 | 库存、人工占用 |
| 消费与维护 | 人口、建筑 | 库存 |
| 人口 | 库存、所在大地块 | 人口实体 |
| 探索与扩张 | 大地块、人口 | 解锁度、探索度、资源揭示 |
| 事项推进 | 进行中事项 | 触发效果 |
| 压力 | 政权、人口、财政 | 压力值 |
| 政权 | 压力、大地块归属 | 政权生灭、分裂 |
| 事件 | 全部（只读） | 触发效果 |

### 5.3 拆分原则

- **按领域拆，不按实体类型拆。** 「人口系统」而不是「PopSystem.update()」。同一领域的规则应能在一个文件里读完。
- **系统之间不直接互调。** 需要协作时，通过写数据让对方在后续阶段读到，或通过效果队列。这是 4.2 那张顺序表存在的意义。
- **一个系统只写自己负责的字段。** 发现需要写别人的字段，通常是拆分错了或者顺序错了。
- **每个系统应能单独测试**：给定 `World` 快照与 `ctx`，输出确定。

## 6. 配置驱动

### 6.1 组织方式

- 配置按**内容类型分目录**，目录决定类型，条目以 ID 命名。新增一类内容 = 新增一个目录 + 一类加载器，不改核心代码。
- 每个条目自带 ID 与显示名，引用一律用 ID。
- **配置是只读输入。** 核心不写回配置，运行时产生的状态一律进 `World`。

### 6.2 加载管线

```
原始文件 → 解析 → Schema 校验 → 交叉引用校验 → 索引化（id → 条目）→ 冻结 → 注入核心
```

顺序不可颠倒：**校验必须在索引化之前**，否则一个拼错的引用会变成运行时的 `undefined`。

### 6.3 校验

启动时全量校验，**失败即报错退出，不做静默兜底**。至少覆盖：

- 每条配置符合其类型的 Schema；
- 所有 ID 引用可解析（Modifier 类型、资源、建筑、科技、效果组、事件）；
- 没有重复 ID；
- 效果引用的操作码合法、参数个数正确；
- 数值在合理区间（负的产量、为零的工期等）。

配置错误在启动时暴露一次，远好过在存档里埋一百次。

### 6.4 版本与兼容

- 配置带版本号，**存档记录其所用的配置版本**。
- 读档时若配置版本不匹配，**拒绝读档并明确报错**，不猜测、不部分迁移。
- 是否提供迁移逻辑，由具体版本的差异大小决定，但**默认是不兼容**。

### 6.5 什么进配置，什么写代码

判据只有一条：

> **新增内容时，你加的是一个 `if`，还是一个求解步骤？**

| 进配置 | 写代码 |
| --- | --- |
| 数值、系数、权重 | 新的机制类别 |
| 有哪些建筑、资源、科技、事件 | 求解算法（市场出清、路径、分配） |
| 条件组合与效果组合 | 性能热点路径 |
| 触发概率、持续时间、前置条件 | 需要跨系统迭代收敛的过程 |

`if` 越写越多的系统，说明它的规则还没被抽象成数据。

## 7. 存档、回放与迁移

- **本局存档** = `serialize(World)` + 种子 + 配置版本 + 之后的命令日志（每条带生效 tick）。
- **局外档案**（遗产点、时代特性、成就）单独存储，**不放进 `World`** —— 它跨局存在，不属于单局状态。
- **回放** = 种子 + 命令流 + 生效时刻，可重放并比对结果。既是排查工具，也是跨实现等价性测试：同一份回放日志喂给任何实现，结果必须一致。
- **表现层不参与存档。** 读档时核心恢复，表现层由全量快照重建。任何"只存在于视图里的状态"在存档后都会丢失，因此影响规则的状态不许只存在于视图层。

## 8. 分层与边界红线

### L0 契约与配置

`Command / Diff / Event / Query / Snapshot` 的结构定义，带版本号；以及全部配置表。契约是唯一的跨层协议，日后换实现时按同一份结构对齐。

### L1 模拟核心

唯一权威状态与全部规则。对外只有窄接口：

| 接口 | 语义 |
| --- | --- |
| `initWorld(seed, config)` | 建局 |
| `applyCommand(world, cmd)` | 入口薄层，折成效果并立即落地，不在 tick 内 |
| `step(world, n)` | 纯模拟推进，无任何命令语义 |
| `query(world, q)` | 只读，不推进 |
| `serialize` / `load` | 存档往返 |

### L2 表现层

渲染、UI、输入捕捉。把玩家意图翻译成 `Command` 发给核心入口，把 `diff / event` 应用到**视图模型**。

### 核心目录内严禁

- 引用 `cc` 或任何引擎、平台 API；
- 规则路径使用 `Math.random`、`Date.now`、任何 IO；
- 除读取配置外自行产生数值；
- 把渲染对象或回调传进核心；
- 在 `step` 内出现「if 玩家命令」类分支。

违反任意一条，会同时破坏可测试性与可替换性。

### 表现层纪律

- 不判定规则、不直接改核心状态，只持有可随时被快照覆盖的派生视图模型。
- UI 组件只走「派发命令」和「发起查询」两个薄接口。
- 需要聚合显示（如大地块概要）时向核心查询，不自己从原始数据推导 —— 两处推导迟早会不一致。

## 9. 目录结构

```
assets/scripts/
  sim-core/          # L0 + L1：纯逻辑，无引擎依赖，可独立测试与运行
    contract/        # 跨层结构定义
    config/          # 配置加载、校验、索引
    world/           # 实体定义、工厂与查询
    mods/            # Modifier 聚合
    effects/         # 效果执行器
    progress/        # 进行中事项
    systems/         # 按领域拆的 tick 阶段系统
    rng/             # 确定性 PRNG
    tick.ts          # 顺序表，模拟的唯一入口
    serialize/       # 存档往返
  view/              # L2：Cocos 场景与 UI 脚本
```

**物理隔离是硬要求：** 核心不 import 表现层，表现层只经 L0 契约访问核心。这样核心可整包搬走、单独跑测试，也不必为视图的存在付出任何代价。
